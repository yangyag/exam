# 프론트 구현 전 백엔드 검토

검토일: 2026-09-11  
기준 커밋: `bbe5f9f`  
범위: `back/app/`, 기존 테스트, `db/`, 문항 적재·검증 도구, 프론트 연동 문서

**기존 테스트 89개는 모두 통과했지만, 별도 재현에서 오류 3건을 확인했다.** 가장 먼저 고칠 부분은 세션 종료와 채점의 동시 실행이다. 그 밖에는 입력 검증 두 곳을 보완하면 된다. 현재 규모에서 전체 구조를 다시 나누는 대규모 리팩토링이 필요하다는 근거는 찾지 못했다.

아래 오류와 별도로, 랜덤 중복 제거 및 시험 화면의 동작 계약 등 프론트 착수 전에 정리할 부분이 있다. 이미 문서에 명시된 제약과 아직 요구사항이 정해지지 않은 기능은 오류로 계산하지 않았다.

이번 작업은 검토이며 백엔드 코드·DDL·문항 데이터는 수정하지 않았다.

## 1. 재현한 오류

| 번호 | 우선순위 | 내용 | 확인 결과 |
|---|---|---|---|
| B-01 | 높음 | 진행 중인 채점이 세션 종료 후 반영됨 | 종료 응답의 `answered=0`이 이후 조회에서 `1`로 변경 |
| B-02 | 보통 | 세션 생성 시 빈 `examId`가 존재 검사를 우회 | `ForeignKeyViolation`으로 HTTP `500` |
| B-03 | 낮음 | `elapsedMs`의 요청 허용 범위와 DB 저장 범위가 다름 | `2147483648`을 보내면 HTTP `500` |

### B-01. 채점과 종료가 겹치면 제출 후 점수가 달라진다

근거: [채점의 세션 조회](../back/app/routers/questions.py#L26), [채점 트랜잭션](../back/app/routers/questions.py#L89), [세션 종료](../back/app/routers/progress.py#L109), [점수 확정 계약](../back/README.md#L238).

채점은 트랜잭션 안에서 `finished_at`을 확인하지만, 해당 세션 행을 잠그지 않는다. 확인과 응답 기록 사이에 `/finish`가 실행될 수 있다. 종료 시점의 점수를 별도로 저장하는 구조도 아니므로, 나중에 추가된 응답이 종료된 세션의 집계에 그대로 포함된다.

실제 PostgreSQL과 HTTP 요청으로 다음 순서를 재현했다. 실행 순서를 확실하게 만들기 위해 **검토용 DB에서만** `study_attempt` 테이블에 잠시 `SHARE` 잠금을 걸어 INSERT를 대기시켰다. 세션 종료와 집계 조회는 통과하는 잠금이다.

1. 새 세션을 만들고 `/answer`를 호출한다.
2. 채점이 `finished_at IS NULL`을 확인한 뒤 INSERT에서 대기하는 것을 확인한다.
3. 다른 요청으로 `/finish`를 호출한다. `200`, `finishedAt` 설정, `answered=0`을 받는다.
4. INSERT 대기를 해제한다. 먼저 시작한 채점이 `200`으로 성공한다.
5. 세션을 다시 조회하면 `finishedAt`은 같지만 `answered=1`로 바뀐다.

이는 **종료가 완료된 뒤 새로 시작한 채점**과 다른 경우다. 그 경우의 `409` 처리는 기존 테스트에서도 정상이다. 누락된 경우는 종료 전에 검사를 통과한 채점이 아직 실행 중일 때다. 프론트에서 마지막 답안 전송과 제출이 겹치거나, PC와 모바일에서 같은 세션을 사용하면 영향을 받을 수 있다.

**수정 방향:** 채점 트랜잭션의 세션 조회에 `FOR UPDATE` 같은 행 잠금을 적용해 종료 UPDATE와 순서를 보장한다. 잠금은 응답·상태 기록이 끝날 때까지 유지해야 한다. 프론트에서도 답안 요청 완료 후 종료를 호출하되, 서버의 점수 확정 조건은 서버에서 보장하는 편이 맞다.

회귀 테스트는 두 순서를 모두 다뤄야 한다.

- 채점이 먼저 잠금을 얻으면 종료가 기다린 뒤 해당 채점을 포함한 점수를 반환한다.
- 종료가 먼저 완료되면 채점이 `409`를 반환하고 응답 이력·상태가 늘지 않는다.

### B-02. 선택하지 않은 회차를 빈 문자열로 보내면 세션 생성이 500이다

근거: [SessionCreate](../back/app/schemas.py#L122), [회차 존재 확인과 INSERT](../back/app/routers/progress.py#L71).

재현 요청:

```http
POST /api/sessions
Content-Type: application/json

{"mode":"random","examId":""}
```

현재 결과는 `500 Internal Server Error`이며 실제 예외는 `psycopg.errors.ForeignKeyViolation`이다.

`SessionCreate.exam_id`는 빈 문자열을 허용한다. 라우터의 `if payload.exam_id`는 빈 문자열에서 존재 검사를 건너뛰지만, INSERT에는 빈 문자열이 그대로 전달된다. DB에는 ID가 빈 문자열인 회차가 없어 외래 키 제약에 걸린다. 프론트 선택 입력의 초기값을 그대로 보내면 생길 수 있다.

**수정 방향:** 빈 문자열을 잘못된 ID로 보고 요청 단계에서 `422`로 거부하거나, 선택값 없음으로 보고 `null`로 정규화한다. 어느 쪽이든 API 계약에 명시하고, 라우터의 존재 검사 기준도 맞춘다. 임의의 DB 예외를 전부 `400`으로 바꾸는 방식보다는 입력 경계에서 처리하는 것이 적절하다.

회귀 테스트에는 생략·`null`·빈 문자열·없는 회차 ID·정상 ID를 포함한다.

### B-03. elapsedMs에 DB 정수 상한 검증이 없다

근거: [GradeRequest.elapsed_ms](../back/app/schemas.py#L102), [study_attempt.elapsed_ms](../db/002_progress.sql#L34).

재현 요청:

```http
POST /api/questions/2026-1-001/answer
Content-Type: application/json

{"choiceNo":1,"elapsedMs":2147483648}
```

현재 결과는 `500 Internal Server Error`이며 실제 예외는 `psycopg.errors.NumericValueOutOfRange`다. 실패 후 응답 이력이 늘지 않는 것은 확인했다.

요청 스키마는 `0` 이상이면 허용하지만, 저장 컬럼은 PostgreSQL `integer`이므로 최대 `2147483647`까지만 저장할 수 있다. 정상적인 몇 분짜리 풀이에서 자주 발생할 문제는 아니다. 다만 프론트가 경과 시간 대신 현재 타임스탬프를 보내는 등의 실수를 서버 오류로 처리하게 된다.

**수정 방향:** 현재 컬럼을 유지한다면 요청에 `le=2147483647`을 추가한다. 더 긴 기간을 저장해야 한다는 요구가 있을 때만 `bigint` 변경을 검토한다. 허용 상한과 상한 초과에 대한 테스트면 충분하다.

## 2. 프론트 착수 전에 정리할 기존 제약과 개선사항

### I-01. 랜덤 출제는 한 번의 응답 안에서도 같은 내용을 내보낸다

근거: [랜덤 조회](../back/app/routers/questions.py#L47), [현재 제약 설명](../back/README.md#L335), 루트 `AGENTS.md`의 중복 출제 방지 지침.

다음 GET 요청의 실제 응답에서 `2023-1-001`과 `2023-1-023`이 함께 나왔다.

```http
GET /api/questions/random?examId=2023-1&count=100
```

두 문항은 같은 질문이며, 보기 2의 쉼표 하나만 다르다. 지문·도식과 나머지 내용도 대조했다. 따라서 ID 중복 제거 또는 원문 문자열의 완전 일치만으로는 이 사례가 걸러지지 않는다. README에 중복 제거 미지원은 이미 명시되어 있지만, 영향은 여러 번 호출할 때뿐 아니라 **한 묶음 안에서도** 발생한다.

중복 없이 랜덤 연습을 제공하려면 API에서 내용 기준의 중복 그룹 중 하나씩 선택하는 기능이 필요하다. 지문·코드·보기·도식을 함께 고려해야 하며, `stem`만 같다고 합치면 서로 다른 문제를 제거할 수 있다. 코드의 기호나 공백까지 무조건 제거하는 정규화도 피해야 한다.

원본 결함을 보존한다는 데이터 정책은 그대로 유지하고, 랜덤 선택 과정에서 처리하는 것이 적절하다. 회차 전체를 원본대로 푸는 화면과 랜덤 연습은 구분한다. 중복을 제외한 후보 수가 `count`보다 적을 때 반환 개수도 문서에 정해야 한다.

### I-02. 시험 모드의 범위·재전송·결과 복기에 대한 계약이 부족하다

다음은 실제 동작 또는 OpenAPI에서 확인한 내용이다. 현재의 단순 학습 기록 방식에서는 의도된 동작일 수 있으므로 모두 오류로 단정하지 않는다.

| 항목 | 확인한 현재 동작 | 프론트 구현에 주는 영향과 개선 방향 |
|---|---|---|
| 회차·과목 범위 | `examId=2026-1`인 시험 세션에 `2022-1-001`을 채점해도 `200`이고 세션 `answered`가 증가함. 채점 시 대상 회차·과목은 조회하지 않음 | 세션을 특정 시험의 점수로 사용할 계획이면 문항의 회차·과목과 비교해 거부해야 한다. 단순 분류용 메타데이터라면 그 의미를 문서화한다. |
| 같은 제출의 재전송 | 동일한 `sessionId`·문항·보기·`elapsedMs`를 두 번 POST하면 둘 다 `200`, `answered=2` | 현재 응답마다 이력을 쌓는 계약과 일치한다. 모바일 네트워크 재시도를 지원하려면 제출별 식별자로 같은 요청의 재전송만 멱등 처리한다. 의도적인 재풀이는 별도 제출로 유지한다. |
| 이어풀기·결과 복기 | 세션 관련 경로는 생성·목록·종료뿐이다. 응답 이력 조회와 세션별 출제 문항·순서 저장이 없다. 정답·해설은 기록을 추가하는 채점 응답으로만 제공됨 | 새로고침 후 세션의 답안과 해설을 복원하거나 다른 기기에서 이어풀려면 추가 계약이 필요하다. 결과 조회만으로 새 응답 기록이 쌓이지 않는 조회 API, 필요하면 세션별 출제 목록 저장을 검토한다. |

근거: [채점 처리](../back/app/routers/questions.py#L78), [세션 집계](../back/app/routers/progress.py#L15), [SessionOut](../back/app/schemas.py#L128), [채점과 진도 기록을 분리하지 않는 현재 계약](../back/README.md#L350).

특히 `SessionOut.answered`와 `correct`는 **응답 횟수의 집계**다. 같은 문제를 반복해서 풀 수 있으므로 고유 문항 수나 최종 답안 기준의 모의고사 점수와 동일하게 취급하면 안 된다. 프론트의 연습 모드에는 그대로 쓸 수 있지만, 모의고사는 답 수정·최종 제출·점수 산정 방식을 먼저 정해야 한다.

### I-03. 복습의 ‘오늘’을 한국 날짜로 볼지 정해야 한다

근거: [복습 예정 뷰](../db/002_progress.sql#L120), [DB 접속 설정](../back/app/db.py#L28).

현재 로컬 PostgreSQL의 `TimeZone`은 `Etc/UTC`이고, 백엔드도 별도의 날짜 기준을 지정하지 않는다. 복습 뷰는 `current_date`를 기준으로 대상 여부와 `overdueDays`를 계산한다.

동일한 시각을 실제 DB에서 두 시간대로 계산한 결과:

| 기준 시각 | DB 날짜 기준 | 한국 날짜 기준 |
|---|---|---|
| `2026-09-12 00:30:00+09` | `2026-09-11` | `2026-09-12` |

한국 날짜를 기대하는 화면이라면 자정부터 오전 9시 전까지 당일 복습 문항이 빠지거나 지연 일수가 하루 작게 표시된다. UTC 날짜를 의도한 서비스라면 현재 구현이 맞지만, 사용자 화면에 적용할 기준이 아직 문서화되지 않았다.

한국 날짜를 선택하면 뷰의 비교 날짜와 지연 일수 계산에 `(CURRENT_TIMESTAMP AT TIME ZONE 'Asia/Seoul')::date` 등 명시적인 기준을 적용한다. 시각 응답을 UTC로 제공하는 기존 계약은 유지할 수 있으며, 역할의 전역 `search_path`나 기존 영어 앱 설정을 바꿀 이유는 없다.

## 3. 리팩토링 판단

현재 라우터·요청/응답 스키마·공용 문항 쿼리·DB 연결의 분리는 규모에 맞다. ORM 전환, 전면적인 서비스/저장소 계층 도입, 모든 목록 응답 형식 통일이 선행되어야 할 근거는 찾지 못했다.

이번 검토에서 수정과 직접 연결되는 정리는 다음 정도다.

- 요청의 값 범위와 빈 값 처리를 스키마에서 명확히 한다(B-02, B-03).
- 채점 트랜잭션 안에서 세션 잠금·종료 검사·필요한 대상 검사를 함께 다루도록 정리한다(B-01, I-02).
- 해당 동작을 실제 PostgreSQL로 확인하는 회귀 테스트를 추가한다. 가짜 DB의 SQL·파라미터 확인만으로는 B-01을 검출할 수 없다.

기존 구조에서 확인된 정상 동작도 있다.

- 문항 조회·목록·통계의 공개 응답에서 정답·해설을 제외한다.
- 응답 이력 INSERT와 상태 누계 upsert가 같은 트랜잭션에 있다.
- 상태 PATCH는 지정한 필드만 갱신한다.
- 없는 대상의 `404`, 종료 후 새 채점의 `409`, 토큰 설정 시 쓰기 가드가 기존 테스트를 통과한다.
- 진도 필터의 `false` 처리와 DB 연결 불가 시 `503` 처리가 테스트되어 있다.

쓰기 재현도 같은 임시 DB에서 수행했으며 작업 후 DB를 삭제했다. 기존 `app.ipe`에는 GET 조회만 수행했고 학습 기록을 수정하지 않았다. `english`·`english_test` 및 역할의 전역 설정은 변경하지 않았다. 테스트 환경은 Python 3.14.7, PostgreSQL 17.10, 저장소 `back/requirements.txt`의 의존성이다.

이 검토는 API·데이터 계약과 확인한 경계 조건을 다룬다. 문항 해설 1,300개의 내용 정확성, 실제 모바일 앱의 동작, 배포 환경의 부하·네트워크 장애 전체를 검증했다는 의미는 아니다.

## 5. 권장 진행 순서

1. B-01을 먼저 수정해 제출 시점의 점수를 확정한다.
2. B-02와 B-03의 입력 계약을 보완한다.
3. 랜덤 중복 제거, 시험의 최종 답안·재전송·결과 복원, 복습 날짜 기준을 프론트 화면 설계와 함께 정한다.
4. 정해진 범위에 필요한 API만 보완한 뒤 프론트 구현을 진행한다. 전체 백엔드를 다시 설계할 필요는 없다.
